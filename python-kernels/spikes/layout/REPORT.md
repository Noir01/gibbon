## Source-confirmed findings

- Constructor order is source declaration order: `gibbon-compiler/src/Gibbon/Language/Syntax.hs:123-127` says canonical order is currently based on original source and `getConOrdering` returns `map fst dataCons`. `Lower.hs:331-342` uses that list's zero-based `elemIndex` as ordinary constructor tag. Thus normalized/reordered representations must be distinguished: tag lookup does not derive order from a normalized numeric layout; it consults the DDef's retained `dataCons` ordering. In this function, indirection/redirection constructors bypass that index and return `indirectionAlt` / `redirectionAlt` (`Lower.hs:333-336`); relative RAN constructors use `150 + ix` (`:337-340`); otherwise tag is `ix` (`:340-342`). `Lower.hs:401-427` excludes indirection/redirection from the info table and records the computed tag plus field-type metadata for the other constructors.
- Generated copySansPtrs is structurally recursive, not a bytewise memcpy: `gibbon-compiler/src/Gibbon/L0/Specialize2.hs:1606-1627` iterates `dataCons` and each constructor's declared `dtys`; fields are processed left-to-right via `zip3 tys xs ys` and `foldr`, recursively copying `PackedTy` fields and forwarding all other field values unchanged before rebuilding the same constructor. This preserves mixed scalar/recursive field sequence; no scalar-field reordering is introduced by this generator. `Codegen.hs:1146-1189` invokes that generated copy function with a fresh output region, then writes precisely `[copy_start, copy_end)` via `fwrite(copy_start, copy_end-copy_start, 1, ...)` and frees the output region/allocation.
- The copy's output allocation is an explicit single region/chunk, not an allocation-growth loop: `Codegen.hs:1146-1161` creates one output region sized by `gib_get_biginf_init_chunk_size()` (`:1167-1170`) and passes its start/end to copySansPtrs. `Codegen.hs:1173-1178` passes NULL as input end, with a comment that it is unused in the copy function. There is no growth/retry in the WritePackedFile sequence; a tree exceeding available output-region capacity is not handled by explicit growth here. This source trace does not establish allocator overflow behavior or a safe tree-size limit; those remain runtime behavior, untested.
- Tag writes are one byte: `Codegen.hs:962-969` stores/loads `TagTyPacked` through a typed pointer and advances one byte. Scalar writes and reads (`:971-979`) cast the cursor to the C type from `scalarToTy`, perform native typed load/store, and advance by `sizeof(type)`. No byte-order conversion or portable encoding is present on these paths. Therefore scalar representation is native-endian/native-C-type, with alignment/unaligned-access behavior dependent on the generated access and target platform; portable encoding is not source-confirmed. The L2 info-table scalar accounting at `Lower.hs:410-427` also counts scalar `sizeOfTy`, excluding packed fields/cursors from scalar-byte total.
- Packed `ReadPackedFile` maps the file directly: `Codegen.hs:1193-1218` obtains `st.st_size`, `mmap`s those bytes, and in packed mode returns the mapped pointer (`:1213-1218`) rather than invoking an unpacker. This is consistent with reading the exact writer byte sequence as packed memory, not decoding a portable interchange format.
